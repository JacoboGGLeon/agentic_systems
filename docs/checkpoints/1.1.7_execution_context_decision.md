# Checkpoint 1.1.7 - Execution Context Decision

Status: implemented and validated locally.

## Initial State

- Grammar and semantics already named a conceptual Execution Context.
- No public or internal `ExecutionContext` symbol existed.
- Runtime, System, policy, state, and evidence had separate owners.
- The earlier audit deferred a final API decision.

## Evaluation

The candidate field set was mapped to `RuntimeConfig`, `AgenticSystem`,
`Agent`, `RunPolicy`, Graph/Environment state, and `RunResult`. Sync and async
Agent execution were traced through the same policy, scheduler, finalization,
and evidence helpers.

The remaining duplication is control-flow symmetry. A container would not
remove those branches, adapter calls, or owner-specific validation.

## Decision

Execution Context remains a normative concept. No public class and no internal
aggregate object are introduced in 1.1.7.

Narrow internal helpers remain allowed when they reduce measured duplication,
but they must not become a second Runtime, System, state owner, or result
envelope.

## Risks Pending

- Future tracing, cancellation, or correlation requirements may need atomic
  propagation across adapter boundaries.
- More execution adapters could create real duplication later.
- The generic word "context" remains overloaded in Tool, Framework, and prompt
  APIs; documentation must continue to qualify those meanings.
