# Checkpoint 1.1.0 - Existing Grammar Audit

Status: complete as an audit; no 1.1 runtime or API changes are authorized by
this checkpoint.

Package baseline: `agentic-systems` 1.0.7.

## Purpose

This checkpoint establishes what the library means today before 1.1 makes the
computational grammar normative. It audits the public API, implementation
ownership, semantic inconsistencies, duplication, compatibility risks, absent
concepts, and missing architectural tests.

Evidence was taken from the curated API inventory, top-level exports, primary
implementations, current architecture documents, and the existing test layout.
The codebase knowledge graph was used for definitions and call relationships;
direct file inspection was used where the graph did not index the `tools/`
sub-package or where documentation text was the subject of the audit.

## Executive Finding

The 1.0.7 implementation already contains the intended grammar, but it does not
yet enforce that grammar as a coherent set of laws. The strongest stable axis is
`Tool/Agent -> RunResult -> observation/validation`. The weakest axes are
composition identity, provider/framework substitution, graph/environment result
boundaries, and the duplicated representations used to bridge portable objects
to runtime registries.

The correct 1.1 strategy is specification and conformance around existing public
objects. A new DSL, a public `ExecutionContext`, or a broad rewrite would add
another representation before the current ones have precise semantics.

## Public API Audit

The source defines 33 recommended names, 103 advanced names, and 104 complete
top-level names. All 104 names in `PUBLIC_API` resolve on the package in the
audited baseline.

The detailed inventory and concept mapping live in
[`docs/GRAMMAR_TO_API.md`](../GRAMMAR_TO_API.md).

Findings:

1. The top-level surface is intentionally curated through `PUBLIC_API`; this is
   a useful compatibility checksum and must be preserved.
2. The "recommended" tier is still broad: it includes provider-resolution
   constants, namespaces, lineage, contracts, output helpers, and two skill
   models. It is a teaching tier, not a minimal grammar kernel.
3. API tier constants are defined in `agentic_systems.api` but are not exported
   from package top level. Existing wording that refers to
   `agentic_systems.PUBLIC_API` as a runtime attribute is inaccurate.
4. `docs/API.md` duplicates the source inventory manually. The recommended list
   and the complete index can drift from `api.py`; source must remain the
   checksum and documentation should be tested against it.
5. Public engine constants coexist with guidance that `engines/` is internal.
   This is valid only if names remain value-level API and implementation modules
   remain private.

## Semantic Inconsistencies

### Tool identity and registration

`@toolkit.tool` returns a `Tool` object. `@system.tool` registers a function in
two registries and normally returns the original callable. `ToolRegistryRuntime`
then maintains a third representation, `RuntimeToolSpec`, and provider paths may
also use `ToolEnvelope`.

Consequences:

- The same conceptual capability has object, function, spec, and envelope
  identities.
- Registration behavior depends on which decorator was used.
- Input schema generation is implemented both by `Tool` and runtime registries.
- `AgenticSystem` must keep `_public_tools` and `_runtime._tools` synchronized.

Required 1.1 direction: define `Tool` as the semantic source of truth and make
adapters preserve identity, schema, and evidence. Do not remove legacy decorator
behavior in 1.1 without a deprecation plan.

### Skill identity

`Skill` is an in-memory runtime package. `LoadedSkill` is a filesystem-loaded
asset with a manifest and optional runtime bridge. `AgenticSystem` exposes these
through separate `runtime_skills` and `skills` collections while combining their
names for lookup.

Consequences:

- "Skill" does not identify one runtime type.
- Registration, validation, assets, and serialization differ by construction
  path.
- A loaded skill can indirectly contain a runtime skill, adding nested identity.

Required 1.1 direction: specify one semantic Skill with multiple materialization
forms. Preserve both public classes while defining conversion and identity laws.

### Agent and System ownership

`Agent` is documented as portable, but direct execution requires a bound system
for most providers. The `agent(...)` factory creates a small hidden
`AgenticSystem`; `AgenticSystem.agent(...)` creates an explicitly owned agent.

Consequences:

- Construction shape affects ownership and lifecycle even when the visible
  `Agent` configuration is equivalent.
- Provider selection, registry availability, and defaults can be inherited from
  hidden or explicit systems.
- Agent identity is not formally separated from binding identity.

Required 1.1 direction: distinguish portable actor definition from execution
binding in semantics and tests. Avoid introducing another public actor class.

### System responsibility

`AgenticSystem` currently owns tool and skill registration, agent creation,
provider hydration, engine caching, graph/environment/eval factories, execution,
and inspection.

This is a practical facade, but its semantic role is ambiguous between container,
composition root, execution context, and governance boundary. For 1.1 it should
remain the public composition/governance facade while internal responsibilities
are clarified behind it incrementally.

### Runtime, provider, engine, and framework

The documentation defines provider as the execution backend and framework as an
adapter. The code still routes providers through canonical "engine" names and
stores `framework` on `Agent`, while some execution implementations live under
`engines/` and others under `providers/`.

Required 1.1 direction:

- Keep provider names and `RuntimeConfig` as public selection API.
- Treat engine as an internal execution mechanism except for existing constants.
- Define framework as an adapter that cannot change core result semantics.
- Test provider and framework substitution with the same fixture contracts.

### Graph, Environment, and Eval boundaries

The conceptual chain is not type-uniform:

- tools and agents return `RunResult`;
- graphs return framework/native state;
- environments return Gymnasium-shaped tuples and retain transition history;
- evals return `EvalReport`.

`AgenticEnvironment` is also specifically graph-backed and record-driven, and
`run_eval` uses an internal environment/step graph. These are valid 1.0 product
choices, but they are narrower than the general concepts in the 1.1 thesis.

Required 1.1 direction: define observation adapters and evidence propagation at
each boundary. Do not force every abstraction to return `RunResult`.

### Result and evidence

`RunResult` is the most mature shared contract. It normalizes text, data, final
answer, tool events, usage, validation, errors, trace, and metadata, and can
validate agent contracts. However, producers construct payloads independently
and graph/environment/eval APIs wrap or project results differently.

The law "no contradiction of result" is not yet executable. In particular,
1.1 must define consistency among `ok`, `final`, `data`, `text`, `errors`, tool
event status, and validation status without breaking historical payloads.

## Duplication And Ambiguous Responsibilities

| Area | Duplication or ambiguity | Risk |
|---|---|---|
| Tool schema | `Tool`, `ToolRegistryRuntime`, and provider runtime specs | Schema drift across adapters |
| Tool output | `RunResult`, `ToolEvent`, `ToolEnvelope`, provider records, output projections | Conflicting status or evidence |
| Skill | `Skill`, `LoadedSkill`, `SkillManifest`, runtime bridge | Identity and lifecycle mismatch |
| Agent construction | direct `Agent`, `agent(...)`, `AgenticSystem.agent(...)` | Hidden ownership/default differences |
| Execution naming | runtime/provider/engine/framework terms | Invalid substitutions and confusing diagnostics |
| Graphs | thin `AgenticGraph` plus specialized environment graphs | Unclear canonical graph contract |
| Validation | pre-run validators, `Agent.validate`, `RunResult.validate`, eval assertions | Undefined ordering and authority |
| Observation | result helpers, human output, lineage, graph state, environment history | Multiple projections without one evidence law |

## Breakage Risks

High risk:

- Changing what `@toolkit.tool` or `@system.tool` returns.
- Collapsing `Skill` and `LoadedSkill` into one class without compatibility
  adapters.
- Renaming provider/engine values or changing `auto` resolution behavior.
- Requiring optional provider/framework dependencies at package import time.
- Tightening `RunResult` consistency validation on historical provider payloads
  before conformance fixtures exist.

Medium risk:

- Moving graph/environment classes while top-level exports remain stable.
- Changing factory defaults, hidden system construction, or agent binding rules.
- Converting environment steps or eval reports to `RunResult`.
- Shrinking the public API based only on the recommended tier.

Low risk:

- Adding documentation-only semantic definitions.
- Adding invariant and conformance tests around current behavior.
- Adding internal adapter protocols that do not alter public construction or
  return values.

## Absent Or Implicit Concepts

The following concepts are absent as first-class semantics or exist only as
scattered implementation details:

- capability effects and side-effect classification;
- determinism and reproducibility declarations;
- execution requirements and dependency capabilities;
- stable identity across object-to-runtime adaptation;
- explicit evidence ownership and provenance rules;
- provider and framework substitution guarantees;
- explicit degradation/fallback records;
- composition compatibility rules;
- lifecycle and state ownership;
- a unified conceptual execution context.

These are specification gaps, not automatic requests for new public classes.

## Missing Architectural Tests

The current tests live under `tests/api` plus fixtures. They provide substantial
behavior and coverage checks, including top-level export checks, provider paths,
contracts, results, environments, and integrations. They do not yet present a
discoverable conformance suite for the 1.1 laws.

Add, in later checkpoints:

| Proposed suite | Required invariant |
|---|---|
| `tests/architecture/test_public_surface.py` | Top-level export checksum and tier/documentation consistency |
| `tests/architecture/test_optional_boundaries.py` | Core import succeeds without optional providers/frameworks |
| `tests/contracts/test_result_consistency.py` | `ok`, errors, validation, final, and tool events cannot contradict |
| `tests/contracts/test_tool_identity.py` | Tool schema and identity survive system/provider adaptation |
| `tests/composition/test_identity_law.py` | Identity composition does not alter observable result |
| `tests/composition/test_explicit_composition.py` | Composition order, ownership, and state are inspectable |
| `tests/composition/test_degradation.py` | Fallback is explicit in result/runtime metadata |
| `tests/provider_conformance/test_run_result.py` | Every provider emits the required result envelope |
| `tests/provider_conformance/test_tool_contract.py` | Equivalent tools preserve schema and evidence across providers |
| `tests/provider_conformance/test_substitution.py` | Provider substitution preserves contract-level behavior |
| `tests/integration_conformance/test_framework_substitution.py` | Framework adapters preserve core semantics and evidence |

Existing regression tests should be reused as fixtures where possible rather
than copied into new directories.

## Refined Checkpoint Sequence

1. **1.1.0 - Existing grammar audit.** Close with this report, the API map, and
   agreement on compatibility anchors.
2. **1.1.1 - Normative grammar.** Define categories, legal compositions, and the
   status of execution context without changing public runtime behavior.
3. **1.1.2 - Semantic contracts.** Define identity, state, effects, evidence,
   failures, and degradation; record unresolved choices as ADRs.
4. **1.1.3 - Executable laws.** Add architecture, contract, and composition tests
   against existing behavior; classify intentional legacy exceptions.
5. **1.1.4 - Result conformance.** Add provider-neutral `RunResult` fixtures and
   resolve contradictions through compatibility-preserving normalization.
6. **1.1.5 - Provider conformance.** Test provider substitution, optional imports,
   runtime description, and explicit fallback.
7. **1.1.6 - Framework and graph conformance.** Specify state/result adapters and
   framework substitution.
8. **1.1.7 - Skill and composition consolidation.** Reduce internal duplication
   while preserving `Skill`, `LoadedSkill`, and factory workflows.
9. **1.1.8 - Executable grammar tutorial.** Validate the full path from function
   through Tool, Agent, System, Graph, Environment, and Eval.
10. **1.1.9 - Release closure.** Run compatibility, documentation, tutorial, and
    package validation before changing the version.

## Recommendation

### Must change in 1.1

- Make grammar and semantic laws normative and testable.
- Establish `Tool` as the semantic capability source of truth across adapters.
- Define actor definition versus execution binding.
- Define result/evidence consistency and explicit degradation.
- Add provider and framework conformance suites.
- Correct API inventory documentation drift and automate its checksum.

### Must preserve

- Simple top-level import and all existing 1.0.7 public names.
- Current Tool, Agent, Environment, and Eval return shapes.
- Optional dependency boundaries.
- Canonical provider names and explicit runtime inspection.
- Existing direct and filesystem skill workflows.

### Must document before implementation

- Identity and equality rules.
- State and lifecycle ownership.
- Effects, determinism, and execution requirements.
- Evidence ownership across graph/environment/eval projections.
- Provider/framework substitution boundaries.
- The conceptual role of execution context.

### Must not build yet

- A grammar DSL.
- A public `ExecutionContext` class.
- A replacement for `RunResult`.
- A new provider or framework solely to exercise conformance.
- A forced unification of `Skill` and `LoadedSkill`.
- A rewrite of `AgenticSystem` or graph/environment APIs.

## Checkpoint Exit Criteria

Checkpoint 1.1.0 is ready for review when:

- the public and concept maps are accepted as accurate;
- the compatibility anchors are explicitly accepted;
- every high-risk change is deferred behind tests and an ADR where needed;
- the refined checkpoint sequence is accepted or amended;
- no version, export, or runtime behavior has changed as part of the audit.

Until those criteria are reviewed, work should not proceed to implementation of
new 1.1 abstractions.
