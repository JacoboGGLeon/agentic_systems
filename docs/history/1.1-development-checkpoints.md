# Agentic Systems 1.1 Development Checkpoints

Status: historical engineering record. Current behavior is defined by the
public API, current contracts and release evidence.

## Baseline Audit

The 1.0.7 audit found an existing but incompletely specified grammar. The stable
axis was `Tool/Agent -> RunResult -> observation/validation`; the principal
risks were silent composition collisions, Provider/Framework ambiguity,
Graph/Environment ownership and duplicated adapter representations.

The accepted direction was to specify and test existing objects before adding
a DSL, public Execution Context or replacement result envelope.

## Delivered Sequence

| Historical checkpoint | Durable result |
|---|---|
| RunResult invariants | Structural validation, recovery evidence and JSON round-trip |
| Tool/Skill composition | Scoped identity, explicit conflict policies and provenance |
| Runtime/Provider substitution | Capability profiles and common conformance reports |
| Framework/Graph boundary | Requested-vs-executed adapter evidence and result projection |
| System/Environment/Eval | Explicit lifecycle ownership, local RNG and reproducibility classes |
| Execution Context | Retained as a conceptual role with no new public object |
| Static inspection | Stable `InspectReport` without Tool/model execution |
| Tutorial/release closure | Public-import policy, evidence boundaries and clean packaging |

## Compatibility Anchors

- Preserve `import agentic_systems as toolkit` and existing top-level names.
- Preserve Tool and Agent `RunResult` behavior.
- Preserve Graph state, Environment tuples and Eval reports as distinct shapes.
- Preserve optional dependency boundaries and canonical Provider names.
- Preserve `Skill` and `LoadedSkill` until a separately tested migration exists.
- Treat engine modules as internal while keeping public engine values stable.

## Deferred Work

The checkpoints deliberately did not introduce a grammar DSL, public
`ExecutionContext`, universal Graph/result type, forced Skill unification or
new Provider/Framework merely to exercise conformance.

Exact intermediate test counts and implementation diffs remain available in
Git history. ADRs 0005–0010 preserve the accepted architectural decisions.
