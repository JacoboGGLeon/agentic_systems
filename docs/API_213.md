# API de Agentic Systems 2.1.3

Construye una unidad, ejecútala y consulta el resultado:

```python
import agentic_systems as toolkit

agent = toolkit.Agent("total", toolkit.Action("sum", lambda data: {"total": sum(data["values"])}))
result = agent.run({"values": [2, 3, 5]})
result.data  # {"total": 10}
```

Para componer unidades se conserva la misma interfaz:

```python
system = toolkit.System("application", toolkit.Sequence((agent,)))
system.run({"values": [2, 3, 5]}).data
```

| Necesidad | Concepto |
|---|---|
| Implementar una operación | Tool |
| Reutilizar capacidades e instrucciones | Skill |
| Organizar el trabajo de una unidad | Agent |
| Coordinar unidades | System |
| Ordenar, paralelizar o decidir | Sequence, Parallel, Graph |
| Procesar episodios con memoria | Environment |
| Comprobar resultados | Eval |

`run` ejecuta y devuelve RunResult. `compile` prepara la misma declaración
cuando se necesita reutilizarla; no es obligatorio. [Seis ejemplos completos](../examples/grammar_tour/README.md)
muestran Agent/System en los tres flujos. Los [tutorials](../tutorials/README.md)
introducen las opciones de forma progresiva.

La referencia siguiente detalla contratos y casos avanzados. Las
[firmas completas](API_213_SURFACE.md) están disponibles para consultar cada
parámetro; no es necesario memorizar todo el inventario para empezar.

## Operaciones y capacidades

`@tool` define una operación determinista síncrona. Sus opciones son `name`,
`description`, `input_schema`, `output_schema`, `metadata`. Los esquemas son
clases Pydantic; no existen los aliases input/input_model/output/output_model
ni strict=False. La operación ofrece `run(input)`, `arun(input)` e `inspect()`.
Devuelve RunResult también cuando falla la validación o la función. Las salidas
son objetos JSON o modelos del output_schema; los números no finitos fallan.

`skill(name=..., tools=..., instructions=..., description=..., version=...,
metadata=...)` agrupa Tools. Tiene datos e `inspect`; no se ejecuta. Las
capacidades se combinan en `Agent.skills=(a,b)`. Las identidades conflictivas
fallan. System no registra otra colección de Skills.

`load_skill(path)` carga exactamente esa carpeta: SKILL.md y skill.py con
`build_skill()`. Permite imports relativos, incluso diferidos mientras se
retenga una Tool. Ejecuta código Python local al cargar; no es una sandbox.
No acepta otros keywords, una Skill ya creada, build() ni register(system).

## Unidades y flujos

```python
toolkit.Agent("worker", flow, skills=(capability,), backend="native")
toolkit.System("application", flow, backend="native")
toolkit.Sequence((first, second), name="sequence")
toolkit.Parallel((first, second), join=combine, name="parallel")
toolkit.Graph(nodes=(("first", first), ("second", second)),
              edges=(("first", choose_next), ("second", "END")), start="first", max_visits=20)
```

Action(name,target,input=...) coloca una Tool, referencia a una Tool de Skill
o función determinista en el flujo. Sequence entrega la salida del paso anterior;
Parallel entrega copias independientes y ejecuta un join explícito solo cuando
las ramas pasan. Graph usa destinos fijos o funciones que reciben el data del
nodo y devuelven un nombre o END. Las decisiones no tienen otro constructor.
Los nodos y pasos tienen nombres únicos. Los ciclos están limitados.

`backend` es native o langgraph. LangGraph construye un StateGraph real con
fork/join y rutas condicionales. El backend exterior no cambia los runtimes ni
frameworks de unidades anidadas. Agent y System pueden contener otros Agents
o Systems; System también admite Actions sin otro registro de Tools.

El mismo Agent puede ser un actor de runtime:

```python
reasoner = toolkit.Agent("reasoner",
    runtime=toolkit.runtime(provider="openai-runtime", model="explicit-model"),
    framework=toolkit.framework("native"), instructions="Use the supplied evidence.",
    skills=(capability,), contract={}, policy={})
```

Se exige exactamente uno entre flow y runtime. Las opciones del actor no se
aceptan en un Agent de flujo. Un backend no nativo sin flujo falla. El actor
puede ocupar un paso de otro Agent/System; no hay bind, pipeline, invoke ni
factories alternativas. Los proveedores externos necesitan modelo explícito
antes de compilar; la configuración suelta puede inspeccionarse incompleta.

## Ejecución

Agent/System: `run(input=None, *, limits=Limits())`, `arun` con los mismos
argumentos, `compile()`, `inspect()`. El preparado ofrece run/arun/inspect.
Environment/Eval y sus preparados usan run/arun **sin input posicional**:
sus inputs ya están declarados. Todos devuelven RunResult.

Compile valida y captura datos sin invocar Tools, routers, callbacks ni crear
clientes de proveedores. Inspect es local. Los límites compartidos
`Limits(max_actions=100,timeout_s=10)` cubren acciones y callbacks del flujo,
episodio, checks y juez. Son cooperativos: un callback bloqueado no se mata.
Los resultados que llegan tarde se conservan. arun usa ejecución en un thread;
cancelar la espera no garantiza cancelar el trabajo.

## Runtime y framework

`runtime` acepta provider/model/region/endpoint/api_key, timeout_s,
max_retries, max_tool_calls, max_turns, max_tokens, backoff_s, max_concurrency.
Los nombres exactos son python-runtime, openai-runtime, ollama-runtime,
bedrock-runtime, vllm-runtime. No hay auto ni fallback. Región corresponde a
Bedrock. Python Runtime es operador determinista, no modelo de lenguaje.
Bedrock con api_key usa bearer; sin ella usa IAM mediante la cadena de AWS.
Las diferencias de configuración por entorno no cambian la gramática.

`framework(name,agent_kwargs=None,run_kwargs=None)` selecciona native,
langgraph, openai-agents o strands. Los adaptadores native y langgraph no
reenvían opciones nativas y rechazan mapas no vacíos. OpenAI Agents y Strands
conservan sus opciones específicas; no pueden sustituir parámetros del ag
ni sus presupuestos. Contexto de aplicación no es configuración del modelo.
Las opciones desconocidas que un SDK no soporte fallan al usarse. Las vistas
de configuración son de solo lectura y su inspect no revela secretos.

## Contrato del actor y salida estructurada

contract es un diccionario cerrado: tool_expectation, completion, failure_policy,
expected_output, expected_tool_outputs, output_schema. tool_expectation usa
all_of/any_of/allowed/forbidden/min_count. No acepta exactly, must_call,
must_not_call ni coerciones de listas/booleanos. completion usa default,
when_required_tools_satisfied o always_finalize. failure_policy usa allow,
no_unresolved o fail_fast. Las contradicciones fallan al compilar.

policy acepta temperature, tool_choice, repair, max_repairs, finalize, trace,
strict. Los presupuestos del actor se declaran solo en runtime. output_schema
es JSON Schema validado localmente; rechaza referencias remotas. La salida
estructurada se comprueba después del actor; no se sustituye un resultado
inválido por uno favorable. Si data está vacío, se puede leer un objeto JSON
de text. Los outputs inválidos conservan datos y evidencia y devuelven ok=False.
El comportamiento de modelos reales requiere validación live separada.

## Environment

Environment(name,unit,records,max_steps=None,memory=None,observe=None,
update=None,stop=None). Cada run abre un episodio nuevo con copia de memoria.
Sin observe, el registro es el input. Los callbacks son:

```python
observe(record, memory) -> input
update(memory, record, result) -> memory
stop(memory, result) -> bool
```

El resultado conserva outputs, history, memoria final, processed, terminated y
truncated. Stop es terminación correcta; un max_steps que deja registros sin
procesar es truncación fallida. Un error de callback conserva los resultados
ya completados. No se promete una API Gym ni interacción streaming.

## Eval

Eval(name,unit,cases,checks=(),judge=None,rubric=None) admite Agent, System o
Environment. Un caso usa name opcional, input, expected. expected acepta solo
ok y data exactos, incluidos tipos. Para un episodio, input puede contener
records y memory. Sin expectativa, check ni juez, el caso se rechaza.

`check(result,case)` devuelve {ok,issues} y opcionalmente metrics, un mapa JSON
de medidas como reward. Las métricas quedan en el informe de cada caso.
El juez es otro Agent explícito que recibe input, expected, result, evidence y
rubric. La rúbrica acepta criteria, threshold, instructions, certification_tool,
require_failure_findings. El juez devuelve criteria con scores, findings y
rationale; ok/score opcionales deben ser consistentes. Criterios fallidos
requieren hallazgos con evidencia. No hay deterministic_authority ni juez
implícito. La aceptación combina ejecución, expectativas, checks y juez por AND.
Un fallo esperado de ejecución puede aprobar su caso conservando el resultado
fallido. El uso de candidato y juez se registra por separado.

## Resultados y trazabilidad

RunResult conserva text/final/data, ok, messages, tool_events, raw_responses,
usage, engine/model/mode, versiones de esquema, validation/errors/meta,
execution_id/parent_execution_id/children. text es presentación textual,
final presentación estructurada y data resultado de cómputo. El esquema de
intercambio es to_dict; `RunResult(**payload)` lo restaura. No expone Pydantic
ni objetos nativos de SDK como otra interfaz.

walk recorre ejecuciones; trace(mode='compact'|'full') presenta evidencia;
lineage(name,question,goal,tags,metadata,max_tool_rows) conserva pasos y decisiones.
La memoria de linaje ofrece to_dict/explain/to_prompt_context. check_invariants
comprueba IDs, parentesco, eventos y coherencia. Las invariantes se verifican en
los límites de ejecución. Una política allow explícita conserva fallos parciales
permitidos, sin ocultar sus errores. Se separan tool_calls e inference_requests.

## Serving

model_artifact declara model/base_model/adapter_path/tokenizer/revision/
quantization/metadata. model_server recibe ese artefacto y keywords explícitos
de profile, endpoint, parsers, GPU, contexto, concurrencia, binario y log; la
[superficie completa](API_213_SURFACE.md) enumera sus defaults. extra_args no
sobrescribe flags gestionados. profile aporta defaults y los valores explícitos
tienen precedencia. inspect y command redactan secretos y no inician procesos.
El ciclo es start/health/stop. endpoint.url y endpoint.model alimentan runtime.
No existen server.runtime, running ni otro constructor de spec/servidor.

La [evidencia offline](../revisions/2.1.3/implementation-evidence/REPORT.md)
separa contratos, fixtures, configuración y rutas no ejecutadas. La [campaña actual](../revisions/2.1.3/framework-evidence/REPORT.md) añade pruebas live con modelos concretos. No publica y mantiene GPU, AWS IAM y ADA IAM pendientes.
